# ДЗ 5. События онлайн-кинотеатра

`POST /events` или генератор → Kafka `movie-events` → ClickHouse `kafka_events` → `save_movie_events` → `raw_events`.

## Запуск

Выполни команды из папки `hw5/`. Kafka, Schema Registry, Movie Service и ClickHouse поднимаются одной командой.

```sh
docker compose up
```

Открой [Swagger](http://localhost:8000/docs) и отправь JSON через `POST /events`. Ниже пример для события паузы.

```json
{
  "event_id": "e97d91eb-8072-4f22-b85a-8b73f56b371c",
  "user_id": "user-42",
  "movie_id": "movie-7",
  "event_type": "VIEW_PAUSED",
  "timestamp": "2026-11-18T18:10:00Z",
  "device_type": "TV",
  "session_id": "session-15",
  "progress_seconds": 600
}
```

Успешная публикация возвращает `201` и `event_id`. Неверные поля дают `422`, ошибка публикации в Kafka даёт `503`. Для нового события укажи новый `event_id`. Для поиска и лайка можно опустить `progress_seconds`.

Чтобы сервис сам генерировал события, запусти его с переменной `GENERATE_EVENTS=1`.

```sh
GENERATE_EVENTS=1 docker compose up
```

## Как проходят данные

1. `kafka-init` подготавливает `movie-events` с тремя партициями и репликацией. При старте Movie Service проверяет топик и регистрирует `movie_event.avsc` как `movie-events-value`. При первой регистрации это версия `1`. Сервис выводит номер версии и ID схемы в лог.
2. Продюсер проверяет данные по Avro, публикует их с ключом `user_id` и ждёт `acks=all`. События одного пользователя попадают в одну партицию, поэтому сохраняется порядок их записи. Клиент Kafka повторяет временно неудачные попытки с растущей задержкой. API и генератор используют один продюсер.
3. При запуске ClickHouse выполняет `clickhouse/01-events.sql`. `kafka_events` читает Avro по схеме из Schema Registry, `save_movie_events` передаёт строки в `raw_events`, а `MergeTree` хранит их. Группировка по месяцам и сортировка по дате и пользователю подходят для запросов об активности за период.

## Интеграционный тест

```sh
docker compose run --rm --build integration-test
```

Команда сама запускает зависимости. Тест отправляет паузу и лайк через API, проверяет ответ продюсера и сверяет все поля в ClickHouse. Новый UUID каждого события изолирует повторные запуски. Отдельная проверка ожидает `422` у события просмотра без прогресса.

Если для доступа к PyPI нужен доверенный сертификат рабочей сети, при пересборке его можно передать как секрет Docker BuildKit `pip_ca` в формате PEM.

## Агрегация и PostgreSQL

`docker compose up` также запускает PostgreSQL и Aggregation Service. Сервис сам создаёт таблицы при старте. Планировщик запускает первый расчёт сразу, затем повторяет его с интервалом `AGGREGATION_INTERVAL_SECONDS` (по умолчанию 300 секунд). Каждый цикл пересчитывает сегодня и восемь предыдущих дат по UTC, чтобы обновлять retention по мере завершения дней наблюдения.

Для ручного пересчёта можно использовать [Swagger](http://localhost:8001/docs) или отправить запрос с нужной датой.

```sh
curl -X POST http://localhost:8001/recalculate/2026-11-18
```

| Метрика | Как считается |
| --- | --- |
| `dau` | Число уникальных пользователей с любым событием за дату. |
| `avg_watch_seconds` | Средний `progress_seconds` среди событий `VIEW_FINISHED`. |
| `movie_views` | Число `VIEW_STARTED` по каждому фильму. При равенстве просмотров фильмы сортируются по ID. |
| `view_conversion` | Число `VIEW_FINISHED`, делённое на число `VIEW_STARTED` за ту же дату. |
| `retention_d1` и `retention_d7` | Доля пользователей, впервые запустивших фильм в выбранную дату и запустивших фильм снова ровно через 1 или 7 дней. |

Доли хранятся числами от `0` до `1` для retention. Конверсия отражает отношение дневных счётчиков, поэтому завершения просмотров, начатых раньше, тоже входят в расчёт. При отсутствии знаменателя или завершённых просмотров соответствующие метрики получают `NULL`. Retention также равен `NULL`, пока день наблюдения ещё не закончился по UTC.

Готовый срез за дату доступен в `movie_analytics.daily_metrics` в ClickHouse. В PostgreSQL таблица `daily_metrics` хранит по строке на дату, метрику и фильм, а также время расчёта. Ручной и плановый пересчёты используют одну функцию. В PostgreSQL повторный расчёт обновляет строки за дату одной транзакцией.

```sh
docker compose run --rm --build aggregation-test
```

Тест проверяет все метрики, повторный пересчёт после добавления событий, результаты в обеих базах и перезапись файла в S3. Для каждого прогона он выбирает свободный диапазон исторических дат.

## Grafana, S3 и репликация Kafka

Если уже запускался одноброкерный вариант, выполните `docker compose up --build`. Первый брокер использует прежний том, а `kafka-init` добавляет реплики к существующим топикам.

| Компонент | Где посмотреть |
| --- | --- |
| Grafana | [Online Cinema](http://localhost:3000/d/online-cinema/online-cinema). Локальный логин `admin`, пароль `local-grafana`. Панели читают готовые агрегаты из ClickHouse. |
| Объектное хранилище | [Консоль RustFS](http://localhost:9001/). Ключ `analytics`, секрет `local-analytics`. Файлы хранятся в `movie-analytics/daily/YYYY-MM-DD/aggregates.json`. |
| Kafka | `docker compose exec kafka kafka-topics --bootstrap-server kafka:29092 --describe --topic movie-events`. |

Строка тепловой карты показывает когорту по дате первого запуска фильма, а столбцы `Day 0`–`Day 7` показывают долю её пользователей, запустивших фильм в соответствующий день. В `Day 0` у непустой когорты 100%. Прочерк означает, что день наблюдения ещё идёт или данные за него ещё не пересчитаны.

Планировщик раз в сутки по UTC выгружает вчерашние метрики из PostgreSQL и обновляет архивы дат, для которых стали доступны D1 или D7. При временной ошибке он оставляет дату на следующий проход. Ручной запрос выгружает уже рассчитанный день. Повторный экспорт обновляет объект по тому же ключу.

```sh
curl -X POST http://localhost:8001/recalculate/2026-11-18
curl -X POST http://localhost:8001/export/2026-11-18
```

Kafka работает на трёх брокерах KRaft. У `movie-events` три реплики на партицию и `min.insync.replicas=1`. Перед стартом Schema Registry одноразовый `kafka-init` проверяет реплики и при обновлении расширяет существующие назначения. После завершения работы этого контейнера `docker compose ps -a` покажет `Exited (0)`.
